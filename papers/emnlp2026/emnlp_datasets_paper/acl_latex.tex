\begin{abstract}
We introduce \datasetname, a comprehensive benchmark for evaluating the capabilities of large language models (LLMs)
in agentic financial analysis tasks requiring tool use. \edit{The benchmark is released in two versions:} (1) \synthsubset,
a synthetic dataset of \edit{5,979} natural-language financial analysis tasks that an agent must solve by issuing structured queries to a tool-callable data environment, with committee-reviewed quality control, and (2) \groundedfinqa,
a grounded dataset derived from FinQA containing 1,108 multi-hop reasoning tasks \edit{embedded in custom tool environments}.
Both datasets require models to \edit{retrieve information exclusively through tool calls} rather than relying on in-context information,
testing genuine agentic reasoning capabilities. We evaluate a range of frontier and open-source models, finding that \edit{even the strongest model achieves only 68.9\% on \synthsubset and 69.6\% on \groundedfinqa, while open-source baselines fall as low as 21.9\% and 16.3\% respectively}, demonstrating significant room for improvement
in agentic financial reasoning. We release the full dataset, evaluation code, and model traces to facilitate future research.
\end{abstract}

\section{Introduction}
%==============================================================================

\edit{\begin{figure}[t]
\centering

\caption{Accuracy on \datasetname grows log-linearly with the (estimated) parameter count of the agent's base model. Closed-source sizes from are taken from the IKP estimates \citep{li2026incompressible}.}

Large language models (LLMs) are increasingly deployed as autonomous agents capable of using tools to accomplish complex tasks
\cite{Schick2023ToolformerLM, qin2023toolllm}. In the financial domain, such agents could assist with financial analysis, compliance
checking, and decision support by \edit{issuing tool calls against structured business data and synthesizing the retrieved evidence into actionable answers}.

However, evaluating the agentic capabilities of LLMs presents significant challenges. Existing financial QA benchmarks like FinQA
\cite{chen2021finqa} and TAT-QA \cite{zhu-etal-2021-tat} primarily test reading comprehension and numerical reasoning over provided
contexts, rather than genuine tool-use and multi-step reasoning. Moreover, many benchmarks suffer from data contamination, where test
examples may have been seen during model training.

We introduce \datasetname, a benchmark specifically designed to evaluate agentic LLMs on financial analysis tasks requiring tool use.
\edit{\datasetname is released in two versions, both produced by the same construction methodology and evaluated under the same agent harness. Practitioners can pick whichever version fits their evaluation budget and source-data preference:}

\begin{itemize}
    \item \edit{\textbf{\synthsubset}: the larger version (5,979 examples), produced by synthetic generation against fresh per-example backing stores accessed through a single structured-data tool. Each example undergoes rigorous quality control through a committee of three LLM judges.}

    \item \edit{\textbf{\groundedfinqa}: the smaller version (1,108 examples), produced by building agentic environments around questions and tables taken from FinQA. Each sample bundles a financial question, a tool environment with diverse custom Python tools, distractor tools and rows, and a gold answer; the agent must perform multi-hop reasoning across several tool calls.}
\end{itemize}

\edit{Both versions share the same design principles. First, answers cannot be extracted from the prompt alone, so agents must use tools to retrieve information. Second, examples require multi-step reasoning with intermediate tool calls. Third, distractor information is present to test the agent's ability to filter relevant from irrelevant data.}

Our main contributions are:
\begin{itemize}
    \item A novel benchmark for evaluating agentic LLMs on financial tasks requiring genuine tool use.
    \item A rigorous dataset creation pipeline with LLM committee-based quality control.
    \item \edit{Comprehensive evaluation of a range of frontier and open-source LLMs used as the \emph{base models} inside the agents,
    revealing significant gaps in agentic financial reasoning capabilities.}
    \item \edit{An open-source release of the complete benchmark together with the dataset-construction pipeline code, the evaluation
    harness, and all model traces. We treat this release as a contribution in its own right, supporting reproducible research and direct reuse of
    our infrastructure for new agentic financial tasks.}
\end{itemize}

\edit{As Figure~\ref{fig:accuracy_vs_size} shows, accuracy on \datasetname grows log-linearly with the parameter count of the agent's base model. This is an expected sanity check that the benchmark's difficulty tracks model capability rather than a task-design artefact, and that performance gaps therefore reflect real differences in agentic competence. Parameter counts for closed-source models are taken from the IKP calibration of \citet{li2026incompressible}.}

\section{Related Work}
%==============================================================================

\datasetname is situated at the intersection of three research areas: context-bound financial Question Answering (QA), general
agentic tool-use evaluation, and domain-specific semantic parsing.

\paragraph{Context-Bound Financial QA}
\edit{Foundational financial benchmarks like FinQA \citep{chen2021finqa}, ConvFinQA \citep{chen2022convfinqa}, TAT-QA \citep{zhu-etal-2021-tat}, and FinanceBench \citep{islam2023financebench} measure numerical reasoning, tabular-textual integration, and reasoning over SEC filings within static, explicitly provided contexts.} These established datasets are inherently
non-agentic as they do not require dynamic interaction or external system calls\edit{; all necessary information is supplied in the prompt, testing reading comprehension rather than tool use or dynamic information retrieval}. Our \groundedfinqa component transitions this
evaluation to a dynamic environment where information must be actively retrieved through multi-hop tool calls, isolating and
testing the core planning and execution logic.

\paragraph{\edit{Agentic and Tool-Use Benchmarks}}
General agent benchmarks, such as ToolBench \citep{qin2023tool, qin2023toolllm}\edit{, MCP-Verse \citep{lei2025mcpverse}, AgentBench \citep{liu2023agentbench}, and SWE-bench \citep{jimenez2024swebench}}, establish the methodological
standard for evaluating LLMs'
planning abilities against a large breadth of tools and domains \edit{(web browsing, code execution, APIs at scale)}. While essential for assessing general tool augmentation, these
benchmarks prioritize scale over domain depth\edit{, and none concentrate on financial analysis with structured-data tools}. Financial analysis critically demands precision and specialized interpretation. By
specializing the tool environment for finance, \datasetname tests the \textit{depth} of financial logic, revealing significant gaps
where general planning skills fail to confer the necessary domain competence (\edit{16--70\% accuracy on grounded financial reasoning tasks}). Recent real-world financial benchmarks like FinGAIA \citep{zeng2025fingaiachinesebenchmarkai},
the Finance Agent Benchmark \citep{bigeard2025financeagentbenchmarkbenchmarking}\edit{, and FinAgentBench \citep{choi2025finagentbench}} prioritize realism by using live web data (SEC
EDGAR\edit{) or SEC-filing retrieval}, while \datasetname is engineered for \edit{\emph{diagnostic fidelity}} using controlled, synthetic environments to attribute failures
unequivocally to flawed planning logic, rather than external noise or API variability.

\edit{\paragraph{Tool Use over Structured Business Data}
A related line of work studies semantic parsing over structured data: cross-domain datasets such as Spider \citep{spider} and BIRD
\citep{li2024can} score a model on the fidelity of a single generated query string against a fixed schema. \datasetname is
deliberately \emph{not} a semantic-parsing benchmark: the agent is never scored on a query string. Instead, \synthsubset evaluates
the full agentic loop (tool selection, multi-turn interaction with the data tool, evidence aggregation across calls, and natural-language
answer synthesis) over financially specialized environments. Two consequences follow that make the task qualitatively different from
text-to-query parsing. First, success requires planning under partial observability: the schema and contents must be probed via tool calls
rather than read from context. Second, financial domain semantics such as accounts-payable aging, variance attribution, and revenue
recognition become first-class evaluation targets rather than incidental surface features. The structured-data tool is the means, not
the end being measured.}

Our approach leverages synthetic data generation and a rigorous quality control process, utilizing a committee of three LLM judges, to
mitigate data contamination risks and ensure high integrity at scale, validating that observed low accuracy reflects genuine
performance limitations.

\paragraph{Data Generation}
Synthetic data generation has proven valuable for creating evaluation benchmarks at scale \cite{wang2022selfinstruct}. Recent work has explored using LLMs to generate and verify synthetic datasets with quality control mechanisms \cite{prabhakar2025apigenmt}. Our approach utilizes these methods and adapts them to creating financial agentic datasets.

\section{Dataset Description}

\subsection{Overview}

\edit{A useful agentic financial benchmark, in our view, must satisfy two requirements at once. First, it should expose the agent to a large, controlled pool of tasks where the ground truth is executable and unambiguous, so that a wrong answer can be traced back to a specific planning or tool-use mistake rather than to evaluator or dataset noise. Second, it should include realistic tasks grounded in human-authored questions over real financial documents, so that the resulting accuracies remain directly comparable to the financial-QA literature that practitioners already use. These two requirements pull in opposite directions: more control means more synthetic data, while more realism caps how many items one can curate. \datasetname therefore comes in two complementary versions (Table~\ref{tab:dataset_overview}): \synthsubset addresses the first requirement, and \groundedfinqa addresses the second.}

\subsection{\synthsubset}
\label{sec:synthsql}

\synthsubset consists of financial analysis tasks that \edit{an agent must solve by issuing structured-data queries through a single tool. Each example is backed by an isolated SQLite store generated specifically for that example; the agent is never required to produce or score a query string, and only the final answer is evaluated.} Each example contains:

\begin{itemize}
    \item \edit{\emph{User role}}: The persona making the query (e.g., CFO, auditor, financial analyst).
    \item \edit{\emph{Query}}: A natural language question about financial data.
    \item \edit{\emph{Backing data schema}: A plausible company-data schema generated for this example.}
    \item \edit{\emph{Backing data}: Realistic financial records including distractor rows.}
    \item \edit{\emph{Expected answer}}: The ground-truth answer.
    \item \edit{\emph{Agent trace}}: A reference solution demonstrating correct tool use.
\end{itemize}

The dataset spans diverse financial analysis categories including:
\begin{itemize}
    \item Accounts Payable (AP) analysis
    \item Revenue recognition
    \item Variance analysis
    \item Data integrity and reconciliation
    \item Financial reporting
\end{itemize}

\edit{Representative queries spanning user roles and task categories are listed in Appendix~\ref{app:example_queries}.}

\subsection{\groundedfinqa}
\label{sec:groundedfinqa}

\groundedfinqa transforms FinQA samples into complete agentic environments. Each example includes:

\begin{itemize}
    \item \edit{\emph{System prompt}}: Scenario description and available tools (without table data).
    \item \edit{\emph{Synthetic backing store}: An SQLite \citep{sqlite} table set reconstructed from the original FinQA tables.}
    \item \edit{\emph{Core tools}}: Functions required to derive the answer.
    \item \edit{\emph{Distractor tools}}: Irrelevant tools to test filtering ability.
    \item \edit{\emph{Correct plan}}: Reference multi-hop solution.
\end{itemize}

Critically, the agent receives only the scenario description and tool definitions, not the underlying data table. This ensures agents must use tools to retrieve information rather than extracting answers from context.

\edit{Representative questions, together with a worked example showing the query, available tools, and a reference tool-call sequence, are given in Appendix~\ref{app:example_queries_v2} and Table~\ref{tab:example}.}

\section{Dataset Creation}
%==============================================================================

\edit{\subsection{\synthsubset pipeline}}
\label{sec:synthsql_pipeline}

The \synthsubset dataset is created through a 9-stage pipeline. \edit{Figure~\ref{fig:pipeline}~(top) gives an end-to-end overview of the \synthsubset construction process; the individual stages are described in detail below.}

\begin{figure*}[t]
\centering
\edit{\includegraphics[width=\linewidth]{figures/main_figure_combined.png}}
\caption{\edit{Construction pipelines for the two \datasetname versions. \textbf{Top:} \synthsubset (9 stages with a committee-judgement gate and an improvement loop). \textbf{Bottom:} \groundedfinqa (9 strictly linear stages, each validated by execution).}}
\label{fig:pipeline}
\end{figure*}

\paragraph{Stage 1: Query Generation}
We start with a few seed queries spanning financial analysis categories (in our experiment, we took 12 seed queries). These seeds are then expanded using an LLM, varying user roles and specific details. We utilize a prompt that takes one seed and generates 20 queries to increase diversity and run it multiple times to generate a large number of queries. We also use embedding-based similarity filtering (cosine threshold 0.9) to remove near-duplicates.

\paragraph{Stage 2: Schema Generation}
For each query, an LLM generates a plausible \edit{data schema} that is: (1) sufficient to answer the query, (2) realistic for a company's records, and (3) appropriately complex.

\paragraph{Stage 3: Data Generation}
The LLM is then tasked with generating realistic data for each query and schema, including: (1) data necessary to answer the query, and (2) distractor rows to increase difficulty. The LLM is also required to provide the correct answer to the query consistent with the generated data.

\paragraph{Stage 4: \edit{Execution-Based Validation}}
All generated \edit{schema and data definitions are validated by execution against SQLite}. Errors are iteratively fixed using LLM assistance (up to 5 attempts). We found that LLMs struggle with fixing small errors in (relatively) long \edit{generated programs}, so we split the program into individual statements and fix them one by one.

\paragraph{Stage 5: Agent Trace Generation}
An agent runs on each query. It is supplied with access to the \edit{example's backing data through the structured-data tool}, with up to 6 rounds of interaction allowed. The full conversation trace is recorded.

At this point, we have a dataset that contains:
\begin{itemize}
    \item A query
    \item \edit{A data schema}
    \item \edit{Backing data (records necessary to answer the query and distractor rows)}
    \item Intended answer to the query
    \item An agent trace demonstrating the solution to the query
\end{itemize}
However, there may be hallucinations, unnatural data, wrong tool calls, or wrong answers in the agent trace that need to be identified and fixed.

\paragraph{Stage 6: Committee Judgement}
A committee of three LLM judges evaluates each example's data and agent trace on five criteria:
\begin{enumerate}
    \item \edit{\emph{Data naturalness}}: Is the generated data realistic?
    \item \edit{\emph{Trace reasonableness}}: Does the agent examine appropriate data?
    \item \edit{\emph{Trace soundness}}: Is the reasoning logical?
    \item \edit{\emph{Grounding}}: Is reasoning based only on tool outputs?
    \item \edit{\emph{Answer correctness}}: Does the answer address the query?
\end{enumerate}

An example passes only if it receives majority approval (2/3 judges) on \emph{all} criteria. In that case, it proceeds to the next stage. Otherwise, it goes to the improvement loop (Stages 7 and 8). Note that the loop only runs once for each example; if the improved example fails the judgement again, it is rejected completely.

\paragraph{Stage 7: Feedback Reconciliation}
The judges' criticisms are given to an LLM which is asked to aggregate them into actionable feedback. The LLM at this stage has access to most of the example's data, including the query, \edit{the data schema, the backing data}, and the agent trace.

\paragraph{Stage 8: Feedback Application}
The agent runs again with a prompt containing:
\begin{itemize}
    \item The query
    \item \edit{The data schema}
    \item The previous agent trace
    \item The feedback produced in Stage 7
\end{itemize}
It still has access to the \edit{structured-data tool}, and the conversation is limited to 6 rounds. The full conversation trace is recorded.

\paragraph{Stage 9: Second Judgement}
The improved examples are then re-judged by the committee. If an example passes, it proceeds to the next stage. Otherwise, it is dropped from the dataset.

\paragraph{Final Filtering}
The final dataset includes only examples that passed committee judgement. We run two filtering passes to ensure quality and complexity of the dataset. The first pass uses an LLM to compare the final answer produced in the agent trace with the intended answer created in Stage 3. Additionally, we filter out examples where the agent did not actually \edit{invoke the structured-data tool} (removing examples answerable from context alone).

\edit{\subsection{\groundedfinqa pipeline}}

The \groundedfinqa pipeline transforms FinQA samples through \edit{9 stages (Figure~\ref{fig:pipeline}, bottom)}:

\paragraph{\edit{Stage} 1: Initial Solution}
An LLM creates a direct Python solution using the original table data, establishing the computational logic.

\paragraph{\edit{Stage} 2: \edit{Backing Data Store Generation}}
\edit{An SQLite-backed table set is generated to model the scenario, containing the records needed to answer the question.}

\paragraph{\edit{Stage} 3: Basic Tools}
Tool functions are created as abstractions over the \edit{backing store}, designed to enable multi-hop reasoning.

\paragraph{\edit{Stage} 4: Correct Plan (Basic)}
A reference solution is written using the basic tools.

\edit{\begin{figure}[t]
\centering
\includegraphics[width=1\linewidth]{figures/fig_pipeline_funnel.png}
\caption{\synthsubset construction funnel: number of examples surviving each stage of the 9-stage pipeline plus the final filtering pass.}
\label{fig:pipeline_funnel}
\end{figure}}

\paragraph{\edit{Stage} 5: \edit{Augmented Backing Store}}
The \edit{backing store} is expanded with additional tables, split data, and distractor rows to increase difficulty.

\paragraph{\edit{Stage} 6: Augmented Tools}
Extended tools are created including:
\begin{itemize}
    \item Core tools for the correct solution
    \item Partial information tools requiring chaining
    \item Distractor tools providing irrelevant data
\end{itemize}

\paragraph{\edit{Stage} 7: Correct Plan (Augmented)}
A reference solution using the augmented tools demonstrates the multi-hop solution path.

\paragraph{\edit{Stage} 8: System Prompt}
A system prompt is generated containing the scenario description and tool definitions, explicitly excluding table data and answer hints.

\paragraph{\edit{Stage} 9: Agent Code}
A runnable agent using the \texttt{smolagents} \cite{smolagents} library is generated for evaluation.

\edit{Each stage is required to output a file (Python code in all stages except Stage 8 which outputs a system prompt with the task formulation). For each stage, the LLM receives in the context:}
\begin{itemize}
    \item A long description of the whole process with all the \edit{stages} described,
    \item An indication of what \edit{stage} is currently running,
    \item All previous files' content from the previous \edit{stages}, and
    \item In \edit{Stage} 9, an example agent code showing coding practices for achieving more stable results.
\end{itemize}
\edit{After completing, each stage undergoes an execution-based validation. If the execution fails, the stage is rerun with a prompt that includes the error message and asks to fix the errors (up to 10 attempts).}

\edit{\section{Experiments}}

\edit{\subsection{Setup}}

\edit{We evaluate a diverse set of LLMs as the agent's base model. The frontier set is GPT-4.1, GPT-4.1-mini, GPT-5, GPT-5-mini, and o4-mini (OpenAI). The open-source set is Qwen3-8B and Qwen3-30B-A3B (Alibaba), and Llama-3.1-8B-Instruct (Meta). Our primary metric is \emph{accuracy}. For \synthsubset, an LLM judge compares the agent's final answer against the expected output and outputs a yes/no verdict; we evaluate on a randomly selected test set of 729 examples for cost reasons. For \groundedfinqa, the numerical answers are compared against the correct plan output with a tolerance of one least significant digit, and we evaluate on the full set.}

\edit{\paragraph{Findings.} Having run experiments on both versions, we observe a consistent picture: overall model capability tracks benchmark accuracy, but the strongest models still leave substantial headroom. The log-linear dependence of accuracy on the agent's base-model parameter count is already visible in Figure~\ref{fig:accuracy_vs_size}, and Table~\ref{tab:results} provides the per-model numbers. On \synthsubset, even the best model (GPT-5) reaches only \emph{68.9\%}, indicating substantial room for improvement; modern and larger models such as GPT-5 outperform smaller, older ones such as Llama-3.1-8B; and the frontier/open-source gap is wide, with even Qwen3-30B-A3B scoring \emph{11\,pp} below the worst frontier model (GPT-4.1-mini). Figure~\ref{fig:synth_categories_radar} further shows that this ranking is stable across the four query categories carried by the seed set: every model's per-category polygon is approximately concentric, so the gap is not driven by any single financial sub-domain.}

\edit{On \groundedfinqa we observe essentially the same ranking. GPT-5 and o4-mini lead at \emph{$\sim$67--70\%}, the GPT-4.1 variants follow, and the open-source models trail. Llama-3.1-8B again severely underperforms its size-matched newer sibling Qwen3-8B, suggesting that tool-use capability is sensitive to the training paradigm and not only to parameter count. Per-model accuracies track each other across the two versions (mean absolute difference \emph{2.6\,pp}); the side-by-side bar chart and the $y=x$ scatter in Appendix~\ref{app:cross_version_results} (Figures~\ref{fig:accuracy_bars} and~\ref{fig:synth_vs_curated_scatter}) make this agreement explicit, with the only material outliers being Qwen3-30B-A3B and Qwen3-8B, which both score noticeably lower on the FinQA-grounded version, where the multi-hop, multi-tool environment exposes more of the weaker models' failure modes.}

%==============================================================================
\section{Discussion}
%==============================================================================

\paragraph{Benchmarking Agentic Capabilities}
Our results demonstrate that \datasetname effectively discriminates between models' agentic capabilities. The significant gap from ceiling performance (around 69\%) suggests current models have substantial room for improvement in financial tool use.

\paragraph{Open-Source Gap}
The large gap between frontier and open-source models (up to 50+ percentage points) highlights an important direction for open-source development. Financial agentic tasks may require specialized training on tool-use trajectories.

\paragraph{Native Tool Calling vs.\ ReAct}
ReAct allows the model to reason before choosing a tool to call. This has a large impact on performance for models that do not reason in their default setting, highlighting the improvement that test-time scaling can bring. For models that are already thinking, ReAct decreases performance. This may reflect that modern thinking models are well-optimized for structured function calling, while ReAct's verbose format introduces additional opportunities for error.

\paragraph{Quality Control}
Our committee-based quality control ensures high-quality examples but introduces potential biases. The judges themselves are LLMs, which may share systematic blind spots with the evaluated models.

%==============================================================================
\section{Conclusion}
%==============================================================================

We introduced \datasetname, a benchmark for evaluating agentic LLMs on financial analysis tasks requiring tool use. \edit{The benchmark is released in two versions: \synthsubset (5,979 synthetically generated examples) and \groundedfinqa (1,108 FinQA-grounded examples).} Evaluation of frontier and open-source \edit{LLMs used as the base models inside the agents} reveals significant room for improvement, with best accuracies of 69\%.

Our work provides a foundation for developing and evaluating financial AI agents. Future work may extend the benchmark to additional financial domains, incorporate \edit{real corporate data sources} (with appropriate anonymization), and develop training approaches to improve agentic financial reasoning.

%==============================================================================
\section*{Limitations}
%==============================================================================

\begin{itemize}
    \item Synthetic data may not capture real-world financial complexity.
    \item \edit{Data schemas are generated, not derived from real companies.}
    \item Evaluation is on English data only.
    \item The committee judges are LLMs themselves, and may share systematic blind spots with the evaluated models.
    \item \edit{The benchmark covers a single structured-data tool and Python-function tool environments; other tool modalities (e.g., web search, document retrieval) are not currently represented.}
\end{itemize}

\section{\edit{Cross-Benchmark Comparison of Size--Accuracy Trends}}
\label{app:cross_benchmark}

\edit{Beyond the within-benchmark sanity check shown in Figure~\ref{fig:accuracy_vs_size}, where accuracy on \datasetname grows log-linearly with the agent's base-model size, we cross-check the size--accuracy relationship on two other recent financial-agent benchmarks. Parameter counts for closed-source models throughout this appendix come from the IKP calibration of \citet{li2026incompressible}; we use the direct estimates from that paper's main table where available and invert the published log-linear calibration on the extended-table IKP scores otherwise.}

\paragraph{\edit{FinAgentBench \citep{choi2025finagentbench}.}}
\edit{On the document- and chunk-ranking tasks of FinAgentBench (Figure~\ref{fig:finagentbench_size}), the trend is the opposite of the one we observe on \datasetname: across the three evaluated proprietary models (Claude-Sonnet-4 at $\approx$237B, Claude-Opus-4 at $\approx$1.4T, and GPT-o3 at $\approx$3T), the \emph{smallest} model wins or ties on every metric (nDCG@5, MAP@5, MRR@5) in both ranking tables. A monotonically negative slope on accuracy versus parameter count is a strong negative signal for benchmark validity. It suggests either that the task probes a narrow stylistic regime that the larger models are over-trained out of, or that smaller models in the same family have been exposed to closely related retrieval data during training. In short, performance on this benchmark appears to be governed more by model-family biases or potential data leakage than by raw model capability.}

\paragraph{\edit{Finance Agent Benchmark \citep{bigeard2025financeagentbenchmarkbenchmarking}.}}
\edit{On the 22-model Finance Agent Benchmark leaderboard (Figure~\ref{fig:financeagentbench_size}), accuracy does increase with parameter count, fitting a roughly $+15.5$\,pp-per-decade log-linear trend. However, the residual variance around this trend is large enough that the fit is not, on its own, a reliable validity signal. First, at comparable sizes models differ by 20--40\,pp; for example, Claude 3.7 Sonnet ($\approx$676B) reaches 44\% while GPT-4o ($\approx$720B) reaches only 20\%. Second, several large models sit far below the trend line: o1 at $\approx$3.5T scores only 21.4\%, and LLaMA 4 Maverick at $\approx$400B scores only 3.1\%, which the source paper attributes to tool-interface misuse. Third, and most strikingly, the same model run in two different reasoning modes can differ by 13\,pp at fixed parameter count (Grok 3 Mini at 30.9\% high-reasoning vs.\ 17.6\% low-reasoning). The positive slope therefore conflates parametric capacity with reasoning paradigm and tool-use training; it does not isolate size as the dominant driver, in contrast to the cleaner relationship observed on \datasetname.}
